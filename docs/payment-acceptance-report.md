补充验证：

- 退款查询补账：支付宝返回 `REFUND_SUCCESS`、本地未记 → 本地置 refunded、扣天、写审计。
- 审计：原因 UTF-8 字节核对一致；before/after 快照包含 plan 与 expiresAt。
- 管理页：登录/退出、订单搜索、详情、查单、退款弹层、用户补发、审计列表全部在浏览器实测。
- 后端日志无 ERROR / 未捕获异常。

## 3. 关键实现口径

- 发货幂等：`orders.status` 从 created 到 paid 只有一次机会；通知与查单共用 `deliverPaid`。
- 金额：全部按「分」比较，忽略支付宝通知中任何未经核对的值。
- 退款：V1 仅整单全额；`out_request_no = out_trade_no`；支付宝确认后才动本地权益。
- 扣天：退哪单扣哪单的 `days`，从到期日往前扣，扣到当天降免费。
- Pro 权益：云端同步（上传 / 拉回）要求有效期内的 Pro；`DELETE /api/data` 不设门槛。
- 管理端：独立账号/会话；未认证统一 404；所有权益变更强制原因并写 `admin_audit`。

## 4. 未覆盖 / 明确不做

- 支付宝对账单下载与自动对账、`alipay.trade.close` 远端关单、部分退款。
- 定时查单任务（当前为用户回跳 + 管理员手动，均有限频）。
- 管理员查看或修改用户训练/饮食/身体数据（产品承诺与安全边界）。

## 6. 复现方式（摘要）

1. 准备临时 MySQL；配置 `server/.env`（参考 `server/.env.example`）。
2. 用 mock 网关或支付宝沙箱配置 `ALIPAY_APP_ID / 私钥 / 支付宝公钥 / ALIPAY_GATEWAY`。
3. 配置 `FITPLAN_ADMIN_LOGIN/PASSWORD`，启动 `java -jar backend/target/fitplan-api.jar`。
4. `npm run dev`，访问 `#/admin` 与用户设置页。
5. 按 T1–T14 逐项操作；真实环境按 T15 补测。
